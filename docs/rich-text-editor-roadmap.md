## 0. 执行摘要

文字处理器已经不是「一个富文本框」：它是一条以 **Tiptap 3 + 自研 OOXML 转换**为核心的本地文档流水线，具备 Office 风格 Ribbon、页面视图、分节、目录/脚注/交叉引用、公式、形状、批注/修订、版本历史、文档库与 4 种导出。与上一轮路线图（`.codebuddy/plans/rich-text-editor-next-roadmap_30481608.md`）相比，页面级排版、文档级能力、Markdown/HTML 导出、模板与拼写检查均已落地。

> 说明：仓库里 `plan/` 与 `.codebuddy/plans/` 属 `.gitignore` 的「Internal」目录，历史路线图与 `progress.md` 是本地内部产物，不在版本库中；本文作为可提交的正式文档放在 `docs/`。

本轮核查后，最值得投入的**不是再堆功能**，而是三条主线：

1. **交付保真**：导入侧与导出侧严重不对称。`.docx` 导出覆盖了大量 OOXML 部件，但导入基于 `mammoth → HTML`，多节、脚注尾注、TOC/REF 域、OMML 公式、图片环绕、页眉页脚变体等「写得出、读不回」（2026-11-13：脚注/尾注、OMML 公式、图片尺寸与左右/上下型环绕已补上导入；多节、页眉页脚变体、TOC/REF 精确页码仍未还原）；修订/批注/形状靠「文本流严格相等」补丁回填，第三方文档容易降级。更关键的是 `fixtures/ooxml-baseline/` **全是 generated 样本、没有真实 Word 二进制**，且基线脚本明确 `continue-on-error`，不是发布门禁（`fixtures/ooxml-baseline/manifest.json`、`scripts/roundtrip-baseline.mjs:7-8`）。
2. **单机可靠性**：全量分页测量、全文档 decoration 扫描、600ms 一次全量 `JSON.stringify` + IndexedDB 写入、localStorage 按字符数而非字节计量、多标签页编辑同一文档无冲突检测，构成「数据不丢、长文档不卡」风险（`PageView.tsx:247-305`、`find-replace.ts:25-43`、`draft.ts:56`、`docStore.ts:177-193`）。
3. **工程质量与可达性**：6 类浮层/面板并存且 Esc 语义叠加（右键菜单 capture 阶段吞键）、6 个模态无 focus trap、ShapeMenu/StyleGallery 有 `role=menu` 但无菜单键盘规范、窄屏溢出菜单跳过 `select`/`color` 导致字体/字号/颜色不可达、打印/草稿恢复/撤销重做/快捷键/窄屏无 e2e（`EditorContextMenu.tsx:151-156`、`Ribbon.tsx:18-36`、`useRibbonCollapse.ts:16`）。

**战略结论**：不与 Word/Pages 做「全功能 + 云协作」的正面对抗（`PRODUCT.md` 明确本地优先与零外发，上一轮路线图也把实时协作/云同步列为「明确不做」）。定位应是「**浏览器里能把一份 docx 安全改完、原样交回去**」的轻量办公工具：把预算投向保真、可靠、键盘与离线体验，再用本地模板/本地 AI 做差异化。

## 2. 现状详细分析

### 2.1 架构与数据流

```
                   ┌──────────────────────── 单一 React 组件（RichTextEditorTool.tsx） ────────────────────────┐
 UI 层              │ EditorToolbar → Ribbon（6 固定 tab + 形状格式上下文 tab） / QAT / 菜单 / 面板 / 对话框    │
 状态层             │ React state+refs（标题、页面设置、审阅、面板开关） │ Tiptap editor（正文真源）           │
 持久层             │ localStorage 草稿（600ms 防抖） │ IndexedDB 文档库 + 20 份版本快照                     │
                   └───────────────┬───────────────────────────────────────┬─────────────────────────────────┘
                                   │ getHTML() / setContent()               │ prepareExportHtml（注入目录/脚注/公式）
                     ┌─────────────▼─────────────┐               ┌─────────▼──────────┐
 导入                │ mammoth → HTML → 消毒规范化 │               │ docx@9 → Packer    │ 导出
 .docx（仅此一种）   │ + 直读 zip 补 sectPr/页眉/  │               │ → 二次改 zip 注入  │ .docx / .pdf / .md / .html
                     │   批注/修订/wps:wsp 形状    │               │   形状/水印/公式   │
                     └────────────────────────────┘               └────────────────────┘
```

要点与证据：

- 入口懒加载 `component: () => import('./RichTextEditorTool')`；`docx` / `mammoth` / `jszip` / `jspdf` / `html-to-image` / `pako` 全部动态 import，构建有 `vendor-tiptap`、`vendor-docx`、`vendor-mammoth`、`vendor-katex`、`vendor-jspdf` 分包（`index.ts:7-28`、`docx.ts:1349`、`pdf.ts:138`、`vite.config.ts:100-114`）。
- 组件树：`EditorToolbar` / `Ribbon` → 左栏大纲、中栏查找替换与审阅/拼写/形状/版本面板、右栏页面设置/模板/文档库/版本历史、编辑区标尺 + 覆盖层 + `EditorContent`、底部状态栏，另有 6 个模态与放映/打印层（`RichTextEditorTool.tsx:1758-2071`）。
- **文档模型 = 单一 HTML 字符串 + 旁路元数据**：批注、修订、页面设置、自定义词典作为草稿字段并存；导出前统一注入目录、脚注尾注、交叉引用与公式（`RichTextEditorTool.tsx:224-245,607-647`；`migrate.ts:26-43`）。
- **架构债**：`RichTextEditorTool.tsx` 单文件约 2200 行、698 个符号，同时承担状态、持久化、导出、面板、对话框与布局；命令在 `ribbonTabs.ts` 以闭包直接绑定 `editor.chain()`，与工具层 `RichTextRibbonActions` 两处维护，无统一命令注册表/快捷键表（`ribbonTabs.ts:89-146,188-220`）。

导入侧 `importDocx` 以 `mammoth.convertToHtml` 为主链路，再用自写 XML 直读补回部分信息（`docx.ts:1180-1246`）。结果是：

### 2.4 UI / 交互一致性

- Ribbon 为数据驱动 `tabs → groups → items`（6 种 item 类型、`onLauncher`、`overlay`、`priority`、折叠 flyout、溢出「更多」菜单），三端共用（`ribbon/types.ts:39-174`、`Ribbon.tsx:18-37,101-219`）。
- 但同一产品内有**四套面板范式**：浮层（查找/样式库/形状库）、文档上方内联（审阅/拼写/形状/版本对比）、左右 aside（页面设置/模板/文档库/版本/大纲）、模态（6 个对话框）。`togglePanel` 只互斥 6 个中栏面板，Find/Outline/对话框/文档库/版本/右键菜单各自独立，可多层叠加（`RichTextEditorTool.tsx:1408-1421,1766-2034`）。
- z-index 散落在 `-1…z-[60]`，多个互不知晓的 `z-50`，无统一 token（`EditorToolbar.tsx:339`、`ShapeMenu.tsx:55`、`EditorContextMenu.tsx:200`、`ribbonTheme.ts:26`）。
- 快捷键只有应用级 `Ctrl/⌘+F` 与 Esc，其余来自 StarterKit 与各组件 `onKeyDown`；「全选」菜单项把快捷键标签硬编码成 `⌘A`，Windows/Linux 显示错误（`RichTextEditorTool.tsx:655-667,1628`）。
- 仅鼠标入口：形状拖拽绘制、resize/rotate 手柄、形状双击编辑文字、右键菜单、链接 `window.prompt`、标尺拖动；`Shift+F10` 与手柄的键盘等价物缺失（`ShapeDrawLayer.tsx:65-105`、`ShapeOverlay.tsx`、`EditorContextMenu.tsx`）。

### 3.3 差距根因（不是功能清单问题）

1. **转换架构单向**：`mammoth → HTML → docx@9` 天然丢弃 OOXML 结构化部件，现有补丁以「文本流对齐」为锚点，遇到第三方文档即降级。要根治，必须让导入侧有一份**结构化中间表示（IR）**，而不是继续加正则补丁。
2. **验证对象是自己生成的**：基线样本全部 `generated`，等于用「自产文档」验证「自产解析器」，掩盖了真实 Word/WPS/Pages 输出差异。
3. **文档模型是 HTML 字符串**：批注/修订/页面设置都在旁路，样式、域、分节无法成为一等对象；这解释了自定义样式、修订模式、结构感知版本 diff 难以实现。
4. **单机能力被当作隐式功能**：草稿、版本、冲突、配额都缺乏显式 UI 与回归测试，用户「以为保存了」但没有任何可核查的反馈。

## 4. 下一步改进增强方案

### 4.1 原则与取舍

- **先保真、再功能**：任何新功能若不能通过 `.docx` 往返样本集，不进入发布。
- **本地优先不可协商**：不引入服务端、账号、默认外发；协作边界保持「文件级异步交付」。
- **不新增框架/UI 库**：继续自研 Ribbon 与面板；新增依赖必须可动态 import 并满足单 chunk ≤500KB。
- **改动落在工具目录**：除共享 Ribbon 的缺陷修复外，框架层零侵入；9 语言文案与体积门禁同步。
- **每个 P0 项都带回归用例**：本轮把「测试债」当成功能交付。

## 附录 A · 术语

- **IR（中间表示）**：介于 OOXML 与 Tiptap 文档之间的结构化描述，用于避免「导出写得出、导入读不回」。
- **保真降级（degraded）**：`docxReview.ts` 中当可见文本流不一致时放弃回填、保留纯文本并提示用户的行为。
- **上下文选项卡**：选中对象时动态出现的功能区选项卡（Word 的「表格工具/图片格式/形状格式」），本工具目前仅形状实现。
- **三端**：文字处理器、电子表格、幻灯片三个共享 Ribbon 展示层的编辑器。
